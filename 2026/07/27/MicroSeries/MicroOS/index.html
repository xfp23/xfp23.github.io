MicroOS：从裸机 Flag 地狱到事件驱动架构

MicroOS：裸机开发的”第二曲线”

项目地址：GitHub - xfp23/MicroOS

查看项目 API 文档

0. 引言：当Flag成为债务

每个嵌入式项目都始于一个优雅的 while(1)。

几个变量、几个定时器、几个flag——简单、直接、可靠。

但当CAN通信、UART协议、传感器融合、故障诊断、数据存储相继入场，系统逐渐异化为：

Flag本身无罪，但Flag驱动的架构有责。 每一次 if(flag) 都是一次隐式耦合：置位者与检查者必须共享状态假设，而状态在时序的迷雾中悄然传播。最终，开发者不是在写业务逻辑，而是在维护一张无形的依赖网。

MicroOS 的诞生初衷很朴素：少写一点flag。但它最终演化为一个轻量级协作式框架——不是RTOS的替代品，而是裸机项目从”能跑”到”好维护”的那条第二曲线。

1. 调度器：把”什么时候跑”还给系统

1.1 问题：main() 不应该是个调度中心

传统裸机中，main() 同时背负两个职责：

  1. 执行业务逻辑（任务做什么）
  2. 管理执行时序（任务什么时候做）

当任务膨胀到十几个，main() 沦为定时器中断的”翻译器”——把Tick翻译成flag，再把flag翻译成函数调用。

1.2 解耦：声明式任务注册

MicroOS 将调度逻辑彻底剥离。用户只声明任务属性，系统负责一切时序：

调度器承诺：在正确的时间调用你的函数，你只需专注函数内部。

1.3 为什么是协作式？

MicroOS 不做抢占式RTOS。所有任务共享同一个C调用栈：

取舍：

  • RAM占用可控（无任务私有栈）
  • 行为可预测（无抢占导致的竞态）
  • 零同步开销（无需信号量/互斥锁）
  • ⚠️ 任务必须主动返回，长任务会阻塞后续调度

设计立场：极端实时性交给硬件中断；MicroOS 负责让”大量普通任务”保持清晰的结构，而非追求纳秒级响应。

2. 通信架构：从”知道对方存在”到”只关心事件”

模块间最大的成本不是功能实现，而是依赖管理。好的架构让生产者不知道消费者是谁。

MicroOS 提供五级通信模型，由轻到重，覆盖所有裸机场景：

2.1 Event：无状态通知

适用场景：按键按下、通信异常、状态翻转——只需知道”发生了”，无需数据。

关键特性：Event 不排队。看到的都是同一个注册时绑定的Userdata。适合”状态通知”，不适合”数据传递”。

3. 安全设计：静态即确定

在资源受限MCU和安全关键领域，动态内存是风险源：

  • malloc() 引入内存碎片
  • 执行时间不确定
  • 长期运行可靠性不可证

MicroOS 的回应是全静态：

资源类型 配置宏 特性
任务表 MICROOS_TASK_SIZE 编译期确定，ID即优先级
事件池 MICROOS_EVENT_POOL_SIZE 静态数组，无碎片
消息事件池 MICROOS_MESSAGEEVENT_SIZE 可整体裁剪（ENABLE=0）
延时池 MICROOS_OSDELAY_POOL_SIZE 静态管理，自动回收
队列 MICROOS_QUEUE_DEPTH × MSG_SIZE 每条Message Event独立实例

结果：RAM占用在编译期即可计算，行为100%可预测。代码设计参考MISRA-C思想，拒绝不可控行为。

  2. 分发所有Message Event（按FIFO出队）
  3. 检查并执行到期OSdelay回调
  4. 按ID顺序运行到期任务

变化的不仅是代码结构，更是设计哲学：

  • 从”我控制一切时序”到”我声明意图，系统保证时序”
  • 从”模块A直接调用模块B”到”模块A发布事件，模块B自主订阅”
  • 从”动态分配，运行时祈祷”到”静态确定，编译期验证”

MicroOS 不试图替代FreeRTOS或Zephyr。它解决的是一个更务实的问题：当裸机项目从几十行增长到几万行，如何不让代码沦为不可维护的Flag地狱？

答案很简单：让裸机保持简单，但让架构承载复杂度。
